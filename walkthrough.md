## 2026-10-07 (Fix CLI forget/purge command tree)

- Findings: `cmd/cli/main.go` declared the top-level `forget` command twice verbatim (a merge artifact), and the `purge` command carried a stray `forget` child — a soft-delete nested under a hard-delete command, which made `stash purge forget` nonsensical. ## 2026-10-14 (Scoped API tokens: read-only and namespace allowlists)

- Findings: A single `STASH_API_TOKEN` grants full read/write access to every namespace, including client data. As soon as more than one agent or client connects, there is no way to limit what each may reach.
- Conclusions: Support several named tokens, each with an optional scope (`rw`/`ro`) and namespace allowlist, configured as JSON in `STASH_API_TOKENS` (`STASH_API_TOKEN` stays as a full-access fallback). Enforce namespaces centrally in the brain so every entry point is covered. Enforce read-only per surface with an explicit read allowlist, because HTTP verbs do not map to read/write: `recall` is a POST that only reads, and MCP is POST-based for every tool. `mcp-go` derives tool contexts from the HTTP request context, so the principal reaches MCP tool handlers.
- Actions: new `internal/scope` (principal on the request context) and a rewritten `internal/auth` (`Token`, `Set`, `ParseSet`, `Require`, constant-time lookup across all tokens, principal injection); `internal/brain/authz.go` with `checkReadAllowed`, `withAllowedSlugs`, and `requireWrite` wired into namespace resolution, `ListNamespaces`, `ListConsolidationRuns`, `CreateNamespace`, and `Import`; `readOnlyWeb` and `readOnlyMCP` middlewares; config `STASH_API_TOKENS`; `bootstrap` builds the set (`Context.Auth`); webui/server/mcp use it; `ErrForbidden`/`ErrReadOnly` map to 403; README, `.env.example`, and both compose templates updated; tests for scope, auth parsing/injection, and the brain guards. Validated with `gofmt`, `go build ./...`, `go vet ./...`, and `go test ./...`.

## 2026-10-09 (Guard reasoner output cost: max_tokens + optional JSON mode)

- Findings: LiteLLM usage data showed the `stash` key spending ~$4.62 in total, almost entirely on 2026-10-08 ($4.13): ~10.3M completion tokens versus 1.9M prompt tokens across 3,769 requests — about 2,745 output tokens per call, for responses that should be sub-200-token JSON. Root cause: the configured model was a reasoning-style model and the reasoner sent no `max_tokens`, so nothing capped the output.
- Conclusions: Output tokens, not the architecture, drove the cost. Added a configurable `max_tokens` guard (default 1024; `0` means unlimited, and the field is omitted when 0 so we never request zero output) and an opt-in `response_format=json_object` (default off, because support varies by provider and an unsupported value returns a 400). The eight identical chat call sites were collapsed into one `chat()` helper so request options live in a single place. The real fix remains choosing a non-reasoning instruct model.
- Actions: `internal/reasoner/openai.go` — added `maxTokens`/`jsonMode` fields, a central `chat()` helper, and switched all 8 reasoner methods to it. `internal/config/config.go` — new `STASH_REASONER_MAX_TOKENS` (default 1024) and `STASH_REASONER_JSON_MODE` (default false). `internal/bootstrap/bootstrap.go` — passed both through to the reasoner. `.env.example` — documented both, with a note to prefer a non-reasoning instruct model. Validated with `go build ./...`, `go vet ./...`, `go test ./...` and `gofmt -l .` (all clean).

## 2026-10-13 (Vijf consolidatie-/recall-bugs gefixt)

- Findings: Codebase-review leverde vijf bugs op. (1) Stage 3.5 (causal links) deelde `cp.LastFactID` met de relationships-stage; die schoof het checkpoint al op, dus causal zag vrijwel nooit nieuwe facts (en bij een fout in stage 2 liep het elke run opnieuw over dezelfde facts). ## 2026-10-13 (Relationship-extractie batchen: 1 LLM-call per 5 facts)

- Findings: Stage 2 (facts → relationships) deed één LLM-call per fact (tot 50 per run), de grootste vaste kostenpost na de output-token-fix. Alleen deze stage is een echte N+1: stage 1 clustert al (1 call per cluster), causal/goal/failure/hypothesis/patterns zijn al batch-calls, en contradictie-classificatie is per feitenpaar en begrensd.
- Conclusions: `ReasonRelationships(fact)` vervangen door `ReasonRelationshipsBatch(facts)`: facts gaan genummerd (`[id] tekst`) in één prompt en elke relatie komt terug met een `fact_id`. De grounding-eis blijft per fact bestaan (entiteiten moeten letterlijk in de tekst van dát fact staan), maar ongegronde items worden nu individueel genegeerd i.p.v. de hele call te herhalen. Default batchgrootte 5 (`STASH_RELATIONSHIP_BATCH_SIZE`), bewust laag: de reply moet binnen `STASH_REASONER_MAX_TOKENS` (1024) passen, anders wordt de JSON afgekapt en faalt de batch. Checkpoint gebruikt dezelfde `contiguousCheckpoint` als stage 1 (nu op ID's), dus een falende batch blokkeert de eerdere niet en wordt de volgende run opnieuw geprobeerd. Verwachte besparing: ~5× minder calls in stage 2 (50 → 10 per run); prompt-tokens per call stijgen licht, output-tokens per fact blijven gelijk.
- Actions: `internal/reasoner/reasoner.go` (interface), `internal/reasoner/openai.go` (`ReasonRelationshipsBatch`, `groundRelationships`, `fact_id` in `jsonRelationship`), `internal/brain/consolidate.go` (stage 2 in batches, `contiguousCheckpoint` op ID's), `internal/brain/brain.go` + `internal/config/config.go` + `internal/bootstrap/bootstrap.go` (`RelationshipBatchSize`), `docker-compose.yml` en `.env.example`; tests `internal/reasoner/openai_test.go`, `consolidate_test.go` aangepast. Validated — gofmt, go build, go vet, go test groen. Niet tegen een echte LLM getest: de promptkwaliteit bij batches is onbewezen.

- Conclusions: De synthese geeft nu een lijst (0..6) facts terug: één fact per losstaande bewering, een lege lijst als er niets blijvends staat (vervangt het oude `summary: null`), en de prompt verbiedt expliciet onderwerpen samen te voegen of één bewering op te knippen. LLM-review), bronnen en contradictiecontrole; twee gelijke facts uit één call ontdubbelen zichzelf. Een cluster telt pas als afgehandeld als al zijn facts lukten (anders volgende run opnieuw; dedup vangt reeds opgeslagen facts op); een cluster zonder facts is meteen afgehandeld, zodat het niet elke run opnieuw naar de LLM gaat. - Actions: `internal/reasoner/reasoner.go` (interface: `[]*StructuredFact`), `internal/reasoner/openai.go` (`structuredPrompt` voor lijsten, `parseStructuredFacts`, `maxFactsPerCall`, nieuwe `ReasonStructured`); `internal/brain/consolidate.go` (lus per fact, `storeFact`, `storeResult`); tests `internal/reasoner/structured_test.go`, `internal/brain/multifact_integration_test.go`, fake reasoner (split op ` || `, `NOFACT`) en prompt-test bijgewerkt. ## 2026-10-15 (Recall: recency decay, stap 1 van 3)

- Findings: Recall was al hybride (vector + Postgres full-text, RRF) en confidence-decay bestaat als achtergrondproces, maar recall zelf gaf geen voorkeur aan nieuwere resultaten. Idee afkomstig uit de vergelijking met Mnemosyne (temporal half-life).

## 2026-10-15 (Recall: as-of queries op facts, stap 3 van 3)

- Findings: `valid_from`/`valid_until` bestonden al, maar recall en `query_facts` kenden alleen "geldig nu" (`valid_until IS NULL OR > now()`): een vervangen of verlopen fact was onvindbaar, dus "wat wisten we op 1 september?" kon niet beantwoord worden.

Let op: `valid_until` wordt ook gezet door confidence-decay-expiry, niet alleen door contradictie-vervanging; as-of ziet dus ook verlopen facts als "toen nog geldig", wat klopt voor "wat geloofden we toen".

Alle rijen hangen aan `namespace_id` en de hiërarchie is de slug-string, dus `substring(slug FROM length(from)+1)` verhuist de hele subtree zonder data te verplaatsen. Bewust zo gekozen: `FOR UPDATE` op de bronrij serialiseert gelijktijdige renames; ontbrekende ouders van het nieuwe pad worden aangemaakt (hetzelfde mkdir -p-gedrag als `create`); een automatisch genoemde rij laat zijn naam met het pad meelopen terwijl een bewust gezette naam blijft staan (anders overschrijft een rename een gebruikerskeuze); root hernoemen en hernoemen in een eigen descendant zijn harde fouten, want die maken de subtree onbereikbaar of oneindig. De HTTP-API is niet uitgebreid: `/api/v1/namespaces/<slug>` parseert alleen het derde paddeel, dus meerdelige slugs zijn daar niet adresseerbaar — een bestaand gat dat een rename-route niet oplost.
- Actions: `internal/brain/namespace.go` (`RenameNamespace`, `RenameResult`, `validateRename`, `parentPaths`, `ErrNamespaceExists`/`ErrRenameRoot`/`ErrRenameIntoDescendant`); `internal/brain/namespace_test.go` (unit-tests plus integratie: subtree verhuist, fact blijft gebonden, en de foutpaden incl. read-only token); `cmd/cli/namespace.go` (`namespace rename <from> <to>`); `cmd/cli/main.go` (registratie); `cmd/cli/mcp.go` (`rename_namespace`); `cmd/cli/mcp_prompts.tmpl` (drie templates); `docs/GETTING_STARTED.md` (tool-lijst).
